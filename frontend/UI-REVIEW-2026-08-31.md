# Frontend review — 31 August 2026

## Scope and safety

Changed only the frontend inside `Desktop/xenon try fix/Xenon` during this review. The original Xenon folder and tourist/mobile pages were not edited. No public-database records were created, changed, or deleted; no real email, payment, or push notification was sent.

## Fixed

- Vendor Notifications, Staff, and Payments now have one main page heading.
- Vendor and admin navigation stays sticky while the document scrolls. Desktop menus scroll internally on short screens; mobile navigation becomes a compact horizontal strip. Mobile admin logout is reachable again.
- Notification inbox/sent pagination and manual refresh are connected to their existing endpoints. Sent records use a Sent timestamp label. Broadcast failures keep the composer and draft; success clears them. Duplicate broadcast submissions are guarded.
- Data reloads clear stale list results and show loading feedback. Synchronous loader failures are caught too.
- Collection normalization returns arrays only, preventing numeric `results` counts or malformed fields from crashing list rendering.
- Package details tolerate legacy text/JSON lists and null entries. An absent cancellation policy is described as missing instead of inventing standard terms.
- Package editing waits for the requested record before saving; stale load results are ignored. Creation/editing reset when switching modes, and submissions are guarded against duplicates.
- Zero values are no longer rendered as a missing value in shared information fields.
- Form labels are connected to login, registration, recovery, and password inputs. Repeated password fields have unique IDs and strength-description IDs.
- A temporary network/server/rate-limit error during token refresh no longer immediately clears the stored session. Rejected refresh credentials still clear it. The backend's exact “token has expired” wording is recognized.
- An unexpected HTML/non-JSON success response now reports a proxy/API configuration error instead of silently looking like empty valid data. Empty HTTP 204 responses remain supported.
- Test configuration supports Node globals, and API import tests work from folder names containing spaces.

## Firebase: not yet connected end to end

The preceding backend-copy work repaired Firebase Admin initialization and notification persistence/routing. This frontend does not yet contain the Firebase messaging SDK, messaging service worker, permission flow, or registration-token upload flow. An inbox API record is different from an operating-system/browser push notification.

### What to open and provide

1. Open the Firebase console and select the same project as the backend service account.
2. Go to Project settings → General → Your apps. Register a Web app if none exists, then copy its web `firebaseConfig` object.
3. Go to Project settings → Cloud Messaging → Web configuration / Web Push certificates. Obtain the public VAPID key (generate a pair if none exists).
4. Provide the web app configuration and public VAPID key for frontend integration. Never put the service-account private key/JSON or server credentials into React, VITE variables, or a public repository.
5. The implementation still needs permission requested from a deliberate user click, a messaging service worker, registration-token saving, foreground handling, and account/logout token cleanup. Test permission denied, unsupported browsers, foreground/background delivery, and account changes.
6. Use HTTPS for deployed push-notification testing. Plain HTTP LAN access is not a production push setup.

Official guide: https://firebase.google.com/docs/cloud-messaging/web/get-started

### Backend blockers found (not changed in this frontend pass)

- `backend/src/services/Core/profileCore.js`, `updateFCMTokenCore`: updates UserModel using `user._id`. Vendor authentication supplies a Vendor document whose user identity is `owner_user_id`; the update can therefore match no user while the endpoint still reports success. Resolve the authenticated owner ID and verify the update matched before enabling vendor web push.
- The current user schema stores one `fcm_token`, not separate device registrations. A second device can overwrite the first. Multi-device delivery and logout cleanup require an agreed backend registration model.
- Firebase credentials/project configuration and real delivery have not been verified by these UI tests.

## Remaining integration limits

- Vendor package/review loaders still rely on the existing public catalogue endpoint and its filtering/pagination. Historical/inactive packages and large result sets need a dedicated contract review; this pass did not invent new backend routes.
- Authenticated writes, approval/payment lifecycles, actual email/OTP delivery, public-database authorization, and real push delivery were deliberately not exercised.
- Strict privacy modes that deny all browser storage and multi-account cross-tab logout behavior need further targeted testing.
